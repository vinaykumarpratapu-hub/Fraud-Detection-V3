# Fraud Detection + LLM Explainability (Portfolio Project v3)

Third project in an AI/ML portfolio series aimed at Senior PM roles in banking/fintech, following
the iPhone Review Sentiment Analysis v1 (TF-IDF + Logistic Regression) and v2 (fine-tuned BERT +
Claude frontend) projects.

**Live demo:** _add your Streamlit Cloud URL here after deploying_
**Dataset:** [PaySim — Synthetic Financial Datasets For Fraud Detection](https://www.kaggle.com/datasets/ealaxi/paysim1)

## What this project demonstrates

Same "brain + frontend" architecture as v2, applied to a structured/tabular banking use case
instead of text:

- **The brain:** an XGBoost classifier trained on engineered transaction features, tuned for a
  severe class imbalance (fraud is ~0.1% of all transactions).
- **The frontend:** Claude (Anthropic API) translates the model's SHAP feature attributions for
  a specific transaction into a plain-English explanation a fraud analyst could act on —
  not just "flagged," but *why*.

## Dataset

[PaySim](https://www.kaggle.com/datasets/ealaxi/paysim1) is a synthetic mobile-money transaction
dataset (built to mimic real transaction logs from an African mobile money provider, since real
banking data is normally locked down for privacy). Each row is a transaction with human-readable
fields: type, amount, sender/recipient balances before and after, and a fraud flag. This repo
trains on a systematic 1-in-10 sample of the full ~6.3M-row dataset (~636K rows, same fraud rate
preserved) to keep the repo lightweight; swap in the full CSV in `data/` and re-run `train.py` for
the complete dataset.

## Methodology

**1. Domain-informed scoping.** EDA showed fraud in PaySim only ever occurs on `TRANSFER` and
`CASH_OUT` transactions — never on `PAYMENT`, `CASH_IN`, or `DEBIT`. Modeling is scoped to those
two types before anything else. This is a real fraud-analytics technique: narrow to the
transaction types that can actually be fraudulent before spending modeling effort, rather than
asking one model to separate five transaction types *and* fraud simultaneously.

**2. Feature engineering.** Beyond the raw balance and amount fields, the model uses:
- `errorBalanceOrig` / `errorBalanceDest`: whether the sender's/recipient's balance actually
  moved by the transaction amount (fraud in this dataset has a near-perfect "account emptied out"
  signature — the strongest single predictor).
- `origEmptiedOut`, `origBalanceZeroBefore`: explicit account-draining flags.
- `destIsMerchant`: fraud never targets merchant accounts in this dataset, only customer-to-customer.
- `hourOfDay`: extracted from the simulator's `step` field.

**3. Handling class imbalance.** Baseline Logistic Regression uses `class_weight='balanced'`.
The main model, XGBoost, uses `scale_pos_weight` tuned to the train-set imbalance ratio. Evaluation
uses precision/recall/F1/PR-AUC throughout — **accuracy is not reported**, because a model that
predicts "not fraud" for every transaction would score ~99.7% accuracy while catching zero fraud.

**4. Explainability.** [SHAP](https://github.com/shap/shap) `TreeExplainer` computes per-transaction
feature attributions (not just global feature importance), which are passed to Claude to generate
a natural-language explanation for each individual prediction.

## Results (held-out test set, 20% split, stratified)

| Model | Precision | Recall | F1 | PR-AUC |
|---|---|---|---|---|
| Logistic Regression (baseline) | 6.8% | 94.3% | 0.126 | 0.487 |
| **XGBoost (main model)** | **100%** | **98.7%** | **0.994** | **0.988** |

**Why the baseline looks so bad on precision:** with `class_weight='balanced'`, Logistic
Regression catches almost all fraud (94% recall) but at the cost of ~2,000 false alarms per ~150
real fraud cases — it can't capture the nonlinear "account was emptied out" pattern that separates
fraud from legitimate large transfers. XGBoost, as a tree-based model, captures that interaction
directly and nearly eliminates false positives.

**A note on the near-perfect XGBoost score:** PaySim's fraud is synthetically generated with a very
consistent signature (drain the sender's account in one shot), so it's far more separable than real
production fraud, which is adversarial and constantly evolving. This is a known property of the
PaySim dataset and is worth calling out explicitly in interviews — don't present 99%+ metrics as
"solved fraud detection," present them as "this model has fully learned PaySim's simulated fraud
pattern, and a production system would need continuous retraining against adversarial, evolving
fraud behavior."

## Deploying (same pattern as v1/v2)

1. **Push to GitHub:**
   ```bash
   git init
   git add .
   git commit -m "Fraud detection v3: XGBoost + SHAP + Claude explainability"
   git remote add origin https://github.com/<your-username>/<repo-name>.git
   git push -u origin main
   ```
   The trained model files in `models/` are small (well under GitHub's 100MB limit), so no Git LFS
   needed this time — unlike v2's BERT weights.

2. **Deploy on [Streamlit Community Cloud](https://streamlit.io/cloud):**
   - New app → point at your repo → main file path: `app/app.py`
   - In **Settings → Secrets**, add:
     ```
     ANTHROPIC_API_KEY = "sk-ant-..."
     ```
   - Deploy. The app works without the key too (falls back to a rule-based explanation and shows
     a warning), so you can verify the deploy before adding the secret.

3. Update the live demo link at the top of this README once deployed.

## Interview talking points

- **Why domain-scope before modeling** rather than let the model learn "these 3 types are never
  fraud" itself — faster training, better precision, and it's the same reasoning a fraud team
  would apply.
- **Why PR-AUC/F1 over accuracy** for imbalanced classification, and what accuracy would have
  hidden here (99.7% accuracy from a model that never predicts fraud).
- **SHAP vs. global feature importance** — global importance tells you what matters on average;
  SHAP tells you what mattered for *this* transaction, which is what an analyst actually needs to
  make a call.
- **Why the near-perfect score is a synthetic-data artifact, not a solved problem** — shows
  awareness that production fraud is adversarial and this result wouldn't transfer as-is.
- **Same v2 architecture pattern, new domain** — classifier is the brain, Claude is the frontend
  that makes the model's output actionable for a non-technical (or time-pressured) reviewer.
